# Interaction feedback

MOS-19 adds optional device-local sound/haptics to vertical card navigation, horizontal card pages, flip-card sides, understanding confirmations and quiz selections. Preferences live in `/settings`, reached from Profile; the page uses the shared account shell and one parent/back link. Sound and haptics are independent, off by default and stored under `mosaic.interaction-feedback.v1`. They are not account progress, are not synchronized, and are not imported from the development prototype's old preferences.

## Triggers and presentation

- User-driven vertical card change: one soft 150ms sine sweep from 640Hz to 160Hz (a short “whoot”), under the sound preference only, with no vibration. Swiper must be initialized, a navigation gesture/key/wheel event must be armed, and the presentation must actually change. Gesture arming expires in the next task, after native event propagation (a microtask would clear it before Swiper's document-level keyboard handler); drag arming clears after touch end/cancel. Initialization, restoration, same-card realignment, canceled swipes, horizontal paging and returning to the feed do not intentionally produce a swipe sound. A wheel-only visit without browser user activation does not queue audio for a later click. A suspended swipe resume older than 250ms is discarded.

- Horizontal InfoCard pages and compact QuizCard panels: a lighter 110ms sweep, 820Hz to 260Hz. FlipCard answer/question transitions: a deeper 180ms sweep, 460Hz to 120Hz. Both share the sound preference, add no vibration, and use the same `createNavigationFeedbackGate`/`useNavigationFeedback` as vertical navigation. Keyboard activation arms the gate before the existing Swiper command; gestures arm it on first slider move. Sound starts on actual index change, while existing FlipCard side persistence and announcements still happen at transition end. Initialization, restored pages/sides, same-side arrow presses, canceled gestures, inactive cards and reduced-motion Swiper remounts do not replay these sounds.
- New eligible understanding confirmation, by button or double tap: a brief check pulse, two rising sine notes (520/780Hz), optional 50ms vibration. Cancellation, blocked/unready confirmation and read-only review do not produce confirmation effects.
- A changed quiz choice: correct selection uses higher rising notes (660/880Hz), optional 50ms vibration and a small option-letter pulse. Incorrect selection uses descending notes (260/220Hz), optional 60ms vibration and a short option-letter opacity transition. No content shaking.
- Same-answer clicks, focus movement with arrows, restored answers, synchronization and feed mounting do not invoke audio/haptics. Quiz effects run from the explicit selection handler, not the feedback-reading effect. Answer correctness still does not award understanding points.
- Existing text feedback, status announcements, focus semantics and progress rules remain intact. Reduced motion removes the new visual effects and preserves sound/haptic preferences. Restoring saved confirmation state does not replay a check animation.

`useInteractionFeedback` owns a lazy player per mounted feed/settings view. Only an explicit action with sound enabled creates/resumes Web Audio. Two short sine notes use low-gain envelopes and finish in about 175ms, with no audio assets or dependencies. A later action, preference change, inactive feed, hidden document or unmount cancels pending/current effects. Unmount closes the context. Audio failures cannot prevent the underlying learning action. A pending resume is invalidated before it can start stale playback.

Preferences validate boolean values, synchronize between same-origin tabs and remain usable in memory if storage fails; Settings reports that limitation. Browser settings and physical output still determine whether effects are heard/felt.

## Vibration capability

Call `navigator.vibrate` only if it is a function; catch rejection/failure and degrade silently. Do not sniff iPhone, Android, operating system or browser names. If an unsupported browser later implements the API, the same enabled preference will work without a device-specific change. An accepted API call is not proof of physical vibration.

The owner heard prototype sound on iPhone and Android, and felt the separate 200ms diagnostic pulse in Android Chrome. The original 12–20ms effects were not felt; the integrated 50–60ms effects still require owner device validation. No physical-iPhone vibration is claimed. See [MDN Vibration API](https://developer.mozilla.org/en-US/docs/Web/API/Vibration_API) and [Web Audio best practices](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices).

## Development preview and verification

`/dev/feedback` remains a development-only presentation preview using the same player/preferences as the real feed. Production renders not-found. It has no study-session provider or progress writes. Its separate 200ms diagnostic reports API absence/rejection/acceptance without promising physical output. Its copy is illustrative; actual learning text comes from the existing cards.

`node --test scripts/interaction-feedback.test.mjs` covers independent/default/malformed/blocked preferences, lazy/muted audio, feature-based vibration, API failure, rapid-action cancellation/context reuse, stale audio resume, hidden documents and audio failure. Existing progress/session tests remain the regression gate. Browser emulation verifies presentation and runtime events; it does not establish physical sound quality, physical haptics or installed-PWA acceptance.

Browser integration checks: Settings switches work with Space, retain both values after reload, and fit at 320px. The shared player creates a running Web Audio graph only after preview activation. An isolated temporary route rendered the actual QuizCard with in-memory answers: arrow keys changed focus without selection/audio, Space selected an incorrect answer with an audio graph, the same-answer Space produced no new audio nodes, and Enter selected the correct answer with reduced motion enabled. The temporary route was removed. Owner account progress was not modified by those checks.

Swipe follow-up browser verification used the real mounted study feed: returning from Profile restored card 203/214 without audio nodes; ArrowDown changed to 204/214, ArrowUp returned to 203/214 and created one oscillator/gain pair; an emulated touch swipe also moved to 204/214 with one pair. A downward swipe restored the starting card. A sub-threshold touch movement created no nodes. Browser-emulated touch is not physical-phone validation. Lint, typecheck, all nine feedback tests and Webpack build passed after this follow-up.

Nested-navigation follow-up: an isolated temporary route rendered the actual InfoCard, FlipCard and compact QuizCard with in-memory state. Restoring InfoCard page 2 and FlipCard answer produced no nodes; an edge ArrowRight produced none. Keyboard page change, answer closing/opening, compact quiz panel change and an emulated horizontal touch swipe each produced one oscillator/gain pair. Reduced-motion FlipCard remount produced none. The temporary route was removed. No learning progress or account state was used in this nested-navigation fixture. The owner still reviews the audible distinction and physical phone behavior.
