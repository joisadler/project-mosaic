# Explicit understanding confirmations

MOS-14 introduces the same **Понятно** toggle for InfoCard, QuizCard, and FlipCard. Viewing, answering, or revealing content never awards progress automatically. Each qualifying confirmation adds 10 percentage points, capped at 100. This is a product indicator of repeated explicit confirmations, not a validated mastery score. Completed cards remain in the feed until MOS-16 delivers review access and normal-feed exclusion together.

## Review and input

- InfoCard: visit every page of the current presentation before confirming. A direct jump to the last page is insufficient.
- FlipCard: reveal the answer before confirming.
- QuizCard: select any answer and expose its explanation. Correctness does not determine progress. In the compact landscape layout, visit the explanation panel; selecting an option alone does not satisfy review.

The accessible toggle is above Read more and the account entry. Feed actions display icons without circular backgrounds, borders, or shadows; invisible hit areas remain at least 44 by 44 CSS pixels, with a keyboard-only focus outline. The selected check uses the section accent and a heavier stroke. `Enter` and `Space` activate it; `aria-pressed` communicates its state. A native progress element and percentage show the current card total. An unavailable action explains its review/spacing condition without awarding points. Touch double-tap on a non-interactive card area performs the same toggle. It ignores code blocks, inline code, links, buttons, quiz options, long presses, movement, scrolling, canceled/multiple pointers, and gestures crossing card boundaries. Existing paging, flip, quiz keyboard semantics, safe areas, and the landscape fallback remain in place. Percentage text and the visible progress fill animate together over 450 ms on confirmation/cancellation, continuing from the current displayed value if interrupted. The semantic progress value updates immediately; saved progress is not replayed as a new award on mount. Reduced-motion preference disables interpolation, and animation frames are canceled on unmount. No decorative animation is added.

## Presentation identity and repeat eligibility

Each confirmation belongs to the stable `session UUID:card ID` presentation from MOS-17. Canceling changes only that confirmation's `active` field. Re-enabling restores the same ID and original award time; toggling, reload, immediate back/forward, page changes, or answering again cannot create additional awards. Earlier confirmations remain intact.

A new presentation of a previously awarded card is eligible only after **10 minutes** and after visiting **5 different other cards** since the previous award. With fewer than 6 eligible cards, visit all other cards; a single-card pool still requires the time interval. New sessions never clear that history. The latest award counts for spacing even if canceled, preventing cancel/restart farming. Re-enabling its original presentation does not create a new repeat opportunity. Constants and the pure eligibility function are in `src/lib/learning-progress/progress.ts`; MOS-13 must reuse this rule instead of inventing a second spacing policy. Feed ordering itself is unchanged here.

## Local persistence

Versioned local storage uses `mosaic:progress:v1:<encoded owner>`, independently of session restart. Guests and each confirmed server account have separate namespaces. An unresolved identity restores no account data; unavailable authentication permits only unsaved browsing. Guest progress stays device-local and separate. The owner explicitly selected no guest-to-account transfer for MOS-22. Signed-in confirmations now synchronize through the account boundary described below.

`ProgressData` contains:

- `confirmations`: presentation-keyed records with a unique confirmation UUID, presentation ID, stable card ID, explicit registry section ID, active flag, creation/update timestamps, and local visit ordinal.
- `reviews`: per-presentation visited page indices, flip-answer exposure, and the quiz option whose feedback was exposed.
- A monotonic local visit ordinal and per-card last-visit ordinals for distinct-card spacing.

The explicit section registry supplies membership; titles and ID prefix heuristics do not. Removed cards and section mismatches are discarded on restoration; page indices and option IDs are checked against current content. Malformed/unsupported data starts safely; read/write failures keep in-memory interaction and expose a storage notice to assistive technology. Browser storage is not encrypted and is not an authorization boundary. No credentials or profile fields are stored in progress.

`createProgressStore` exposes cached snapshots, subscriptions, review updates, a toggle operation, and confirmation reconciliation. Reconciliation replaces only confirmations: local review history, visit ordinals, and the separate study session are retained. For an unseen remote confirmation, the current local visit ordinal becomes its conservative spacing baseline; visit counters from different devices are never compared.

## Account synchronization

`GET /api/study-state` reads the authenticated account's state. `POST` accepts explicit confirmation mutations, selected section IDs, or a scoped reset. Both derive ownership from `requireUser`; client-supplied ownership/navigation fields are rejected. Responses are uncached. Mutations require the exact configured origin and JSON, validate registry membership and stable UUIDs, and cap requests at 100 confirmations / 128 KiB. The MongoDB `studyState` collection has one document per server user ID. Its unique `_id` and revision compare-and-swap prevent concurrent overwrites. No database credentials reach the client.

Each presentation stores its confirmation UUID, active flag, timestamps, record version, and last mutation UUID. Percentages are derived from active records and capped at 100, never merged by adding totals. Replaying a mutation cannot add another award. Cancel/re-enable changes only that presentation. Independent presentations from different devices merge; simultaneous edits of the same record use the expected record version, with the current server record winning a stale conflict. Client wall clocks do not choose a winner. Offline actions retain the review/spacing decision made on their device; synchronization does not invent a globally ordered visit history or retroactively enforce cross-device spacing.

The client writes an account-specific outbox and last cloud snapshot to `mosaic:sync:v1:<encoded account owner>`. Existing signed-in local confirmations are reconciled by stable IDs; guest storage is never read for account migration. New local actions update the displayed progress immediately and enter the durable outbox before asynchronous upload. Updates to one presentation coalesce to its latest choice. An edit made during upload is rebased against that upload's acknowledgment. Successful reads merge cloud records underneath pending local actions. Server conflicts discard the affected pending edit and expose a conflict notice on the account page. Unknown/removed content is filtered through the explicit registry.

Requests time out after 15 seconds. Temporary failures retain the queue, retry with exponential delay (1–30 seconds), and expose a readable account status plus a retry button. Online, focus, and visible-page events trigger another attempt; successful clients poll every 30 seconds. A `401` stops automatic retries until an explicit retry/lifecycle event; the UI asks the user to sign in again. Storage failures fall back to memory and explicitly warn against closing before upload. This is an outbox for an already loaded app, **not offline app loading**: no service worker or offline asset cache is added.

Sign-out/account switching aborts and disposes the old controller, removes its data from the displayed context, and leaves its private local outbox available if the same account returns. A request already accepted by the server may finish for that original account; it cannot write another account's document. The study session's order, current card, page, quiz choice, and flip side never enter this API. Account progress can change without restarting or moving the feed.

Selected sections have a separate version and mutation UUID, default to all registered sections, and follow the same queue/conflict policy. `setSections(ids)` is consumed by the first MOS-15 increment: hierarchical chapter/subsection checkboxes (including partial chapter state), Select all, Clear all, and feed filtering on `/account`. Guests save versioned IDs in `mosaic:sections:v1:guest`; account choices use the existing outbox. Empty selection is preserved, obsolete IDs are discarded, and newly added sections stay unselected after an explicit preference has been saved. Unconfigured defaults include the available sections. Filtering preserves confirmations and presentation identities; completed cards are not excluded. `resetProgress(cardIds)` performs online account-scoped resets after flushing pending changes and checking the current cloud revision. For guests, it removes only those cards' local confirmations and persists through the local progress store, without network access or account/selection changes. A reset removes only the targeted confirmations and increments those cards' reset generations. Old offline mutations carry the old generation and cannot restore reset progress. Resets are not queued offline. An ambiguous failed reset must be reread/reviewed before a new explicit attempt; the server operation itself is idempotent for the same mutation UUID. No selection/reset UI was introduced by MOS-22. MOS-15 now supplies aggregate progress and confirmed reset controls for subsections, whole chapters, and the entire inventory.

## Aggregate progress and reset controls

The account page shows each subsection, chapter, and overall average across all unique cards in that scope, including unselected and untouched cards. Each card contributes its capped confirmation percentage; a chapter average is weighted by actual card count, not an average of subsection averages. Completed/total counts use cards at 100%; nonzero progress does not imply completion. Percentages display up to two fractional digits so early progress remains visible. An empty scope yields zero without division errors. If identity cannot be verified, the UI reports progress unavailable instead of presenting an account total of zero.

Reset controls are available when the scope has confirmation history, including canceled awards. A native modal dialog names the exact scope, explains that it cannot be undone, distinguishes guest-device and account-wide effects, and requires a second explicit action. Initial focus is Cancel; Escape/cancel makes no change and returns focus. While waiting, controls are disabled. Success refreshes derived totals and restores focus to the trigger, or to the section heading if that trigger became disabled. Failure stays in the dialog with a readable warning: an uncertain server response does not prove that nothing changed, so the user must review before retrying. Resets preserve selected subsections, review exposure, local visit history, and the study session UUID/order/position/page/answer/side; only a subsequent explicit confirmation can award progress again. Completed-card exclusion/review remains separate MOS-16 work.
