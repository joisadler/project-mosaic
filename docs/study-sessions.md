# Device-local study sessions

The feed restores its order and position from `localStorage` on the same origin and browser profile. No session position is sent to MongoDB or synchronized to another device. Localhost, a development tunnel, production, private browsing, and separate browser profiles have separate storage. Clearing site data removes the saved session; unavailable storage falls back to an in-memory session and a notice on the My learning page.

## Profile and learning navigation

The feed profile icon opens `/account` (Профиль): authentication/profile/sign-out plus summary links to `/learning` (Моё обучение) and `/review` (Повторение). My learning contains subsection selection, detailed progress, scoped resets, synchronization/storage notices, and the confirmed shuffle action. It provides explicit profile and study return links. All four routes share the mounted study layout; inactive feeds remain inert. Back from My learning restores focus to its profile entry; other route changes focus the destination heading or feed return control. Direct links and reloads use the same owner-scoped stores. Application Settings will be added only when actual preferences exist; accordions and visual redesign are separate tasks. ## Saved state

The versioned snapshot stores a random session UUID, canonical stable card IDs, current card ID, informational page indices, selected quiz option IDs, and flip sides. Continuous study additionally stores a bounded presentation queue and current entry ID, with interactions keyed by presentation. See [Study ordering](study-ordering.md) for migration, pruning, and round rules. Explanations are derived from the selected quiz option; scroll offsets and transient focus/animation state are not stored. Presentation identity is `round UUID:card ID`, stable across reload and backward/forward navigation in retained history; the initial round and finite review use the session UUID as that prefix. The separate [learning-progress store](learning-progress.md) uses this identity for explicit understanding confirmations; the session store itself never awards progress.

Keys have the form `mosaic:session:v1:<encoded owner>:<encoded scope>`. Owners are `guest` or `account:<server user ID>`. Identity comes from the shared Better Auth session client. While identity is unresolved, no previous account session is displayed or overwritten. If authentication is unavailable, browsing uses a separate unsaved session until identity can be confirmed. Sign-out/account switching remounts the session boundary and restores only the new owner's state. Nothing is automatically imported from guest to account. Browser storage is not encrypted or a security boundary against someone controlling the same browser profile; the snapshot contains no credentials, name, or email.

The scopes are `study:all` and `review:all`, each with its own persistent UUID, canonical order, current card, pages, quiz choices, and flip sides. Section selection projects a filtered view of that canonical session, preserving its UUID, full saved order, and all card interactions. Surviving cards retain their order and current position; if the current card is excluded, the view chooses the next surviving card or the final surviving card. An empty selection has an empty view with a settings entry. Updating a filtered view writes interactions back without replacing the full order. Re-enabling a section preserves retained presentation identities and cannot award progress; replenishing a depleted filtered queue follows the documented round policy. The Swiper instance remounts when the visible inventory changes, using the same session UUID. Explicit study restart alone creates a new study UUID; it leaves the review session intact. Study projects unfinished cards; review projects completed cards at 100%. The two mounted feeds preserve their independent navigation across account/mode round trips. Inactive feeds are hidden, inert, excluded from the accessibility tree, and have global input disabled. The review context cannot record exposure or mutate confirmations. Entering review does not restart study or create a new study presentation.

## Recovery and starting again

Malformed snapshots and unsupported versions start a new session. Existing valid orders retain surviving cards, remove duplicate/deleted IDs, and append shuffled new IDs. If the current card disappeared, resume at the nearest remaining position. Informational pages clamp to their new page count; invalid quiz options and flip sides are discarded. Empty feeds remain navigable to My learning (`/learning`) or the profile when identity is unavailable.

The My learning page's **Перемешать ленту** action asks before replacing the current local session, assigns a new UUID, reshuffles, clears its quiz/page/flip presentation state, and returns to the feed. It does not clear study progress. The separate subsection/chapter/all-progress reset controls clear confirmations without replacing this session or its saved interactions. The ordering policy generates a fresh round; constraints in small pools can still produce the same card order with new presentation identities. Existing guest/other-account snapshots are unaffected. Multiple tabs in the same browser profile use the same saved namespace; each mounted tab retains its current session and the last interaction to write storage wins. This does not implement live tab synchronization.

Storage reads happen once when the client subscribes; snapshots are cached through `useSyncExternalStore` with a matching empty server snapshot for hydration. Each meaningful interaction writes synchronously, so leaving for Read more does not rely on an unload handler. Write failures never block navigation. No dependencies, service workers, or general-purpose state framework are added.
